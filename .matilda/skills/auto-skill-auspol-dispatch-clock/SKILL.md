# auspol dispatch clock — anatomy, verification, and the 2026-10-10 audit findings

Read this before editing `.build/dispatch-clock/`, triaging a red `coverage-check`
heartbeat, or implementing fixes the user approved from the audit. The README in
that directory covers deploy/ops; this skill is the code-and-failure-modes map.

## What it is

A Cloudflare Worker (cron `* * * * *`) that reads the GENERATED
`.build/dispatch-clock/schedule.json` and POSTs `workflow_dispatch` to
api.github.com for every slot due in that Australia/Sydney minute. GitHub's own
`schedule` trigger ran the updater workflows 2–5h late at the median in Sep
2026 and dropped Roy Morgan's whole Monday window twice; the workflow files
keep their (tuner-generated) cron blocks as the backup. Live since 2026-09-24.

## Files and their roles

- `worker.mjs` — thin runtime shell: `scheduled` → `ctx.waitUntil(tick(...))`;
  `fetch` → read-only status JSON (Sydney clock + next 12 dispatches;
  since 822eb6c a table-load failure answers 503 JSON instead of an
  unhandled Worker exception). No secrets beside the `GITHUB_TOKEN`
  binding.
- `clock.mjs` — runtime-free logic shared by Worker and tests: `sydneyClock`
  (Intl formatToParts, `hourCycle: "h23"` so midnight is `00`), `dueWorkflows`
  (exact day+HH:MM match, `SAFE_WORKFLOW = /^[a-z0-9][a-z0-9-]*\.yml$/` rejects
  path-poisoned table entries — .yaml names silently never fire),
  `fetchTableOnce`/`loadTable` (fetch with `cf:{cacheTtl:300}` — retunes take
  ~10 min to reach the Worker — retried in-tick over `[0,500,1500]`ms with a
  5s abort: Cloudflare never retries a cron event, and a single-attempt read
  used to lose the whole minute), `tick` (sequential dispatch loop, body
  `{ref:"main"}`, 204 = started; since dfcc9cc each workflow's dispatch is
  try/catch-isolated — a failure logs `console.error`, reports
  `{workflow, status:"error"}`, and can't abort the rest of the minute;
  since 822eb6c the dispatch POST carries `AbortSignal.timeout(10_000)` —
  a hung GitHub socket used to stall every workflow queued behind it in
  the minute).
- `served.mjs` — reads the clock's work back out of GitHub's run list (the
  Worker keeps NO record): `backup` mode (poll-agent.yml `clock` job,
  cron-triggered runs only) skips the update when every instant of the cron
  line in 24h has a dispatch run within EARLY 1m/LATE 5m that `didWork` —
  completed+success, OR in-flight but FRESH (`now - created` within
  TWIN_MS=15 min: a prompt cron must not double its own slot, but a run
  queued/in_progress for hours is stalled, not served, and the backup
  runs). Any doubt fails OPEN (runs the update). `heartbeat` mode
  (coverage-check.yml, daily) counts table slots in the trailing 24h
  (15-min settle) — scoring only instants ≥ the table's `generatedAt`+15
  min, so a retune that adds/moves slots can't read yesterday's
  impossible-to-serve slots as misses — with a `workflow_dispatch` within
  ±10 min claimed GREEDILY 1-to-1 nearest-first (a run midway between two
  comb slots serves ONE slot); ≥90% healthy, ≥50% degraded (warning), under
  that exit 3 → job red → email. Since 822eb6c a table with NO slots is
  `inconclusive` (exit 1), never healthy: an emptied schedule.json
  dispatches nothing, and due=0 would otherwise read as a quiet day.
  Test seams: `SERVED_NOW`, `SERVED_RUNS`.
- `schedule.json` — GENERATED by `tune-schedules.mjs` (TABLE_ABOUT +
  FIXED_SLOTS: np-score 07:15, prediction-refresh 13:00, both "twin of its
  cron line"). Since dfcc9cc it carries `generatedAt` — the slot list's
  last-change stamp, preserved across regenerations whose slots are
  JSON-identical, so a no-op weekly tune (the DST pass included) doesn't
  reset the heartbeat's scored window. ~511 slots, ~661 dispatches/week,
  peak day ≈127 runs (Mon) — comfortably under the 10×100/run-list
  pagination caps. Pushed by schedule-tune.yml, which since 822eb6c runs
  `node .build/test-dispatch-clock.mjs` as a gate before pushing it.
- Tests: `.build/test-dispatch-clock.mjs` pins Sydney-minute matching across
  DST BOTH ways, the committed table's integrity (every workflow exists +
  accepts workflow_dispatch; slots non-empty; NO Sun/daily 02:xx slot —
  Sydney's DST edge hour repeats in autumn and skips in spring, so a slot
  there would dispatch twice or never), the exact API call (incl. the
  AbortSignal on the dispatch POST), cronMatcher POSIX semantics, the
  backup skip rule and heartbeat thresholds.

## Live verification recipe (read-only, worked 2026-10-10)

```sh
# is the clock serving? group today's workflow_dispatch runs by workflow:
gh api "repos/:owner/:repo/actions/runs?event=workflow_dispatch&per_page=100&created=%3E%3D<ISO>Z" \
  --jq '.workflow_runs | group_by(.path) | map({wf:(.[0].path|split("/")|.[-1]),n:length})|sort_by(-.n)'
# heartbeat health: recent coverage-check outcomes
gh run list --workflow=coverage-check.yml --limit 4 --json conclusion,createdAt
# when did a slot set enter the table (false-alarm checks):
git log --format='%h %ad %s' --date=short -5 -- .build/dispatch-clock/schedule.json
node .build/test-dispatch-clock.mjs
```
Slot counts by day: `node -e` over the table (see the 2026-10-10 audit: Sat
has 0 weekday slots, so a weekday-only house landing on Saturday dodges the
heartbeat false alarm below).

## The 2026-10-10 audit: six findings, ALL fixed — dfcc9cc (MATILDA.md notes in 236b8a5)

The audit found: single-attempt tick, no persistent logs, the heartbeat
judging yesterday against today's table, non-bijective ±10-min matching,
FIXED_SLOTS twin cron drift in AEDT, and didWork trusting in-flight runs
forever. All six fixed in commit dfcc9cc ("fix all" → "push when done"):
the mechanisms above ARE the current code. The fixes, for archaeology:

1. `clock.mjs` — `fetchTableOnce`/`loadTable` retry the table read in-tick
   (`[0,500,1500]`ms, 5s abort); per-workflow try/catch isolation in `tick`.
2. `wrangler.toml` — `[observability] enabled = true` (Workers Logs persist;
   a failed dispatch's `console.error` used to survive only in a live
   `wrangler tail`).
3. `schedule.json` `generatedAt` — the heartbeat scores only instants
   ≥ stamp+15 min; the stamp is preserved across slot-identical
   regenerations. (EMRS's 160-slot/week addition on 2026-10-10 was the
   forcing case — its survivor out was a Saturday with zero weekday slots.)
4. Heartbeat run-matching is greedy 1-to-1 nearest-run with a used set —
   a run midway between two comb slots counts once.
5. `# tune-fixed:begin/end` regions in np-score.yml + prediction-refresh.yml:
   tune-schedules.mjs rewrites the FIXED_SLOTS twins' own cron lines with
   the DST offset in force on every tune (`fixedTwins` statuses; TUNE_STATUS
   gains `twins`); dfcc9cc moved both files to their AEDT lines.
6. `didWork(r, now)` bounds in-flight trust at `TWIN_MS = 15*MIN` — a stalled
   run is not-served, so the cron backup fires. (Pre-fix had been recorded
   as an accepted trade-off; it is now fixed outright.)

**Deployed:** findings 1–6 are LIVE as Worker version 90c4e8df (deployed

## Hard boundaries / gotchas

- Never hand-edit `schedule.json` (generated) or cron lines inside generated
  marker regions — `# tune-schedules:begin/end` (house blocks) and
  `# tune-fixed:begin/end` (the two FIXED_SLOTS twins, since dfcc9cc):
  change the recipe in `tune-schedules.mjs`.
- The token is a fine-grained PAT (Actions: read+write, this repo only) that
  WILL expire; the heartbeat existing *is* the alarm — "token expired" is the
  first hypothesis on any red heartbeat, then check raw.githubusercontent
  availability (a pre-dfcc9cc table-read failure silently lost the minute;
  now retried in-tick) and whether a retune just moved the table (the
  generatedAt gate should make that a non-event — if a red heartbeat still
  follows a retune, suspect the gate itself).
- `clock.mjs` is imported by both the Worker and Node tests — keep it free of
  runtime APIs beyond global `fetch`.
- The backup's fail-open is deliberate: a cron line it can't read, an API
  error, a slot the clock never carried (Essential's 05:02 skip-confirm,
  DemosAU's hourly gate), a DST-stale UTC cron line, or a failed dispatched
  run must ALL run the update. Don't "fix" any of those to skip.
- `.wrangler/` (local deploy state) is gitignored on purpose.
